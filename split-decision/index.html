Validation that tells the truth

A model that scores 0.98 until you split the data by patient.

A microscope slide gets cut into hundreds of patches, and a patient often has several slides. Shuffle the patches into train and test and the model is graded on near-copies of what it studied: same person, same tissue, same stain. Below is a synthetic cohort of 190 patients from three hospitals, one simple model, and four ways to split it. Each is compared with what actually happens next year, at a hospital the model has never seen.

All synthetic. Each patch is a 16-number embedding, the kind an image encoder produces, generated as site color + patient look + tumor + noise, so it's known exactly how much each part contributes. The model is k-nearest neighbours, because when it cheats you can see whom it copied. Nothing leaves your browser.

Four splits, one reality

Site A is a referral center: 80% of its patients have cancer. Site B is a community hospital: 15%. Site C is in between. That difference is the trap.

What each split says the model can do

Patch-level AUC on the split's own test set. 0.5 is a coin flip, 1.0 is perfect. The dashed line is the same model, trained on everything, scored on 120 new patients from Site D. Click a bar for details.

Whom the model copied

Every patch, squashed from 16 numbers to 2 (the top two principal components). Patches from one patient clump together, and so do patches from one site. Lines run from a sample of test patches to the training patch the model found closest. Red means it found the same patient: the answer was in the training set.

Split on the right key, and check it in SQL

The data is a hierarchy. Whatever level you split on, everything above it can land on both sides. Split on the patient and nothing about a person leaks; split on the site and nothing about a hospital does either.

The split, as a query

A hash of the key decides the side, so re-running never reshuffles and every team gets the same split. This is the selected strategy; the page does the same thing with a different hash function.

How this maps to a real build

      
    
        
  • 
          
    Keys from the source system
    
          
    Patient, accession, part, block and slide ids come from the lab information system, not from file names. The
            medical record number is replaced with a stable pseudonymous key before anything reaches the analytics
            project, so splits can key on the patient without seeing who they are.
    
        
    • 
        
  • 
          
    One split table, versioned
    
          
    Splits are made once, in BigQuery, with a hash of the patient key, and stored as a table with a version.
            Every experiment records which split version it used. A new cohort extends the table; it doesn't reshuffle it.
    
        
    • 
        
  • 
          
    Leakage as a data test
    
          
    The overlap query runs as a test (a dbt test, or a scheduled query that fails the Airflow DAG) between
            building the training set and launching the training job. A failure blocks the run.
    
        
    • 
        
  • 
          
    Validation that matches deployment
    
          
    If the model will be used at new sites, hold out whole sites. If it will be used next year, hold out the most
            recent months. Report the patient-level split too, but don't headline it.
    
        
    • 
        
  • 
          
    Remove the shortcut
    
          
    Stain normalization or color augmentation at training time, so site color can't stand in for diagnosis.
            Check by training a model to predict the site from the embeddings: if it can, so can the diagnosis model.
    
        
    • 
        
  • 
          
    What production adds
    
          
    Vertex AI Pipelines (or Kubeflow) with the split version and data snapshot as pipeline parameters. Slide-level
            and patient-level metrics alongside patch-level ones. Subgroup results by site, scanner and stain batch.
