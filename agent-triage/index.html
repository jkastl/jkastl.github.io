Multi-agent systems, simulated

Watch agents triage a service desk, and see where they're not trusted.

Requests come into the fictional Northwind Health Data Platform's service desk. A router agent picks a specialist, the specialist calls tools, and guardrails, a policy gate and a human reviewer decide what's actually allowed to happen. Pick a scenario and watch the trace, or type your own request.

This is a simulation of the architecture, not a live LLM. Routing and agent "reasoning" are rule-based, and latencies and failures come from a seeded generator, so a scenario plays the same way every time. All people, datasets and tickets are made up. Nothing leaves your browser.

    How this maps to a real build

    The pattern is the one I'd build with Google's Agent Development Kit (ADK) in Python. Here's what each piece on the page would be in that setup.

    • Agents

      The router is a coordinator LlmAgent with the three specialists as sub_agents. It hands off by transferring control, and each specialist has its own short instructions and only its own tools.

    • Tools

      Plain Python functions with type hints and docstrings; ADK turns them into function tools. Reads and writes are kept apart, and write tools take an idempotency key so a retry can't open a second ticket.

    • Guardrails as callbacks

      Redaction and injection screening run in a before_model_callback, so the model only ever sees cleaned text. The write gate is a before_tool_callback: it can refuse a call outright, and it re-checks policy in code instead of trusting what the model concluded.

    • Sessions and human approval

      A session service stores the conversation and its state, so a run can stop for an approval and pick up later. The approval step is a long-running tool that waits on the reviewer's answer, then the run resumes from the session.

    • Cloud Run and the ITSM

      The agent runs as a Cloud Run service. The ITSM (ServiceNow or similar) calls it from a webhook when a request is filed; the agent writes back through the ITSM's REST API. A queue in between handles bursts and retries.

    • What production adds

      Eval sets that check routing and tool sequences on every change. OpenTelemetry traces (this page's trace panel, for real). An append-only audit log of every decision and approval. One least-privilege service account per tool, with secrets in Secret Manager.
